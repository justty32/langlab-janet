# team-model — 誰來做：角色三層、聰明度分級、選人判準

[WORKFLOWS](../WORKFLOWS.md)｜[INDEX](../INDEX.md)

本檔記**誰來做**——分幾層角色、每層派哪一級的模型、按什麼順序選人。本專案沒有導入 multi-agent 包的 inbox／dispatch（那是跨資料夾 agent 往來用的），所以這裡只留**選人**這一段；同 repo 另一條線的活狀態照舊記在 [SESSION-LOG](../SESSION-LOG.md)。

**何時用**：要開一組 agent 平行做事、要決定某一層派哪級模型。
**何時不用**：一兩個檔的小改、純查詢——自己做完就好，開團隊的成本比省下的時間高。

## Done when

- 這一輪要開的每一層都**指名了誰**——頂層、領導、工人各自是哪一格。
- 交出去的每條線都寫死了**範圍**與**驗收條數**（見 [speed](team-model/speed.md) 的靜態對策）。

## 一、角色三層

### 頂層 agent（使用者直接面對的那一個）

職責四件：接收指令、開 agent 團隊、傳達指令、**協調使用者自己也會用到的資源**（鍵盤滑鼠螢幕，乃至 CPU、硬碟、網路）。**資源授權的源頭是使用者**——頂層只是代為分配，**不能自己創造授權**。

頂層只轉達與調度，**比領導笨是正常的**：計畫不在頂層做。本專案使用者明說「主 session 盡量不要自己做事」，所以頂層預設把活往下派，自己只留協調。

對使用者說話要**適合使用者理解**：初次出現的東西先用白話講一句。**預設不必翻譯**；翻譯本身吃太多 context 時，改成直接指出**該先看哪些檔**。

頂層通常可以有**自己的私人輔助者**（查資料、盤點），不必事事經過領導。輔助者**不算團隊 headcount**。

### 團隊領導（＝計畫制定者）

職責：把目標拆成計畫、派工、監看、核驗、收線。

負擔重（計畫＋指揮＋匯報），所以**模型下限比工人高**——這一層要先訂一個下限級別，不從便宜格裡挑。**若「制定計畫」被分出去給某個成員，領導只剩指揮與匯報，就可以降一級。**

領導自己 context 吃緊時**寫 state 檔交棒**（本專案寫 [SESSION-LOG](../SESSION-LOG.md)），不硬撐。

### 工人

依任務難度／內容，加上**使用者給的 headcount**，配便宜模型。工人自己再開子 agent **我們不管**——它在那一層就是領導；我們只告訴它**那邊能用多少資源**。

## 二、聰明度分級與本專案派工

級別是**使用者定的總分**，不是某一項能力的分數。新增用途欄（調查、寫作、實機操作…）時**只加欄、不改既有級別**。

| 級 | 誰 | 用途細分 |
|---|---|---|
| S | Fable | 目前唯一的 S；本專案派**困難的事** |
| A | Opus | **軟體工程**；本專案派**普通的事**（含領導層）|
| B | Opus | 軟體工程之外 |
| C | Sonnet | 本專案派**簡單、機械性的事** |

**本專案的派工分級**（2026-09-19 使用者原話）：可以開**無限個 agent**，主 session 盡量不要自己做事；**困難的 → fable，普通的 → opus，簡單的 → sonnet**。偏好本體登記在 [common/user](common/user.md)。

對應到本 repo 的實際工作：

| 事情 | 難度 | 派誰 |
|------|------|------|
| 設計新主題的教學結構、改 kernel／工作流、跨多檔重構 | 困難 | fable |
| 寫一篇教學、補 reference 一節、修 bug、寫測試 | 普通 | opus |
| 照樣式補一列表格、改連結、跑指令貼回輸出、格式統一 | 簡單 | sonnet |

## 三、token 消耗速度

兩條規則：

- **同一廠商內**通常**與聰明度成正比**——越聰明越貴。
- **不同廠商的同級模型可以差到兩級**，所以這張表**要自己實測填**，不能照抄別人的。

重點是推導出來的那一格：**「聰明度高、消耗速度低」的那一格就是性價比之神，工人層大量用它。** 本專案目前只用 Claude 系列（Fable／Opus／Sonnet），消耗與聰明度成正比，沒有那一格；所以省的辦法是**把簡單的活切乾淨交給 sonnet**，不是找便宜的聰明模型。

## 四、選人判準（按序看這六項）

1. **任務難度／內容**——決定聰明度下限。
2. **使用者給的 headcount**——本專案是**無限**，但見第 5 項。
3. **token 消耗速度**——工人層大量用便宜模型，貴的留給真的需要的那幾件。
4. **溝通方便與否**——跨體系即使有信箱仍有成本，所以**領導層不建議跨體系模型**。
5. **管理上限**——**開太多領導不好管**；寧可少開領導、把量壓在工人層。headcount 無限不等於該開滿。
6. **時程**——用「產出速度 × 繞圈數 × 模型癖好」反推每段派誰、排多久，算法見 [speed](team-model/speed.md)。

## 五、context 管理

每層管自己下級的 context——管得好就是清雜訊，直接提升決策品質。五條規則見 [context](team-model/context.md)。
