# 37 · 什麼操作貴

從 C++ 過來的人會想知道「這行的成本是多少」。Janet 沒有這種文件，
所以**這篇的每個數字都是在這台機器上量出來的**，不是查來的。

⚠ **先講最重要的話**：下面的絕對數字**沒有意義**（換台機器就變），
有意義的是**倍數**與**排序**。而且大部分情況下這些差異你根本不用管——
只有兩個地方是真的會痛的，先講那兩個。

## 兩個真的會痛的

### 一、在迴圈裡用 `string` 累積字串

```janet
(var s "") (for i 0 20000 (set s (string s "x")))    # 134.7 ms
(def b @"") (for i 0 20000 (buffer/push-string b "x"))#   0.4 ms
```

**三百倍上下**（重跑會在 300～330 之間晃，別記死）。因為 `string` 每次都**造一個新字串**並把舊的整個抄過去——
累積 N 次就是 O(N²)。`buffer` 是可變的，直接往後接，O(N)。

這跟 C++ 裡 `std::string operator+` 在迴圈裡的問題一模一樣，
差別是 C++ 你至少有 `reserve` 可以救，Janet 就是**換 `buffer`**
（兩者的分工見 [18 字串與 buffer](18-字串與-buffer.md)）。

### 二、在迴圈裡「造一個新集合」而不是往裡塞

```janet
(var a @[]) (for i 0 20000 (set a (array/concat @[] a i)))   # 403.9 ms
(def a @[]) (for i 0 20000 (array/push a i))                 #   0.3 ms
```

**一千倍以上。**同一個道理：每圈重造整個陣列是 O(N²)。

> 這兩條合起來是一句話：**迴圈裡不要造新容器，往可變容器裡塞。**
> 這是 Janet 效能問題的第一名，而且差距大到不用量就該避開。

## 不用管的那些

**查一個元素**（30 萬次）：

| 操作 | 時間 |
|------|------|
| `(arr 500)` array 索引 | 4.0 ms |
| `(st 500)` struct 查鍵 | 4.5 ms |
| `(tbl 500)` table 查鍵 | 5.1 ms |
| `(get-in d [:a :b])` 兩層 | 38.2 ms |

array／table／struct **三者差不多**，都是 O(1)。
**別為了查詢速度在它們之間糾結**——照語意選（要不要可變、要不要當鍵，見
[35 拷貝與凍結](35-拷貝與凍結.md)）。

⚠ 唯一的例外是 `get-in`：它比直接查**慢八倍**，因為要走一遍路徑清單。
熱迴圈裡先把中間層取出來存著，別每次 `get-in`。

**走訪一千個元素**（300 次）：

| 寫法 | 時間 |
|------|------|
| `(map inc arr)` | 10.9 ms |
| `(seq [x :in arr] (inc x))` | 11.0 ms |
| `each` ＋ `array/push` | 10.8 ms |

**完全一樣。**所以 `map`／`seq`／`each` 之間**照可讀性選**，
不要因為「聽說推導比較快」去改寫（見 [32b loop 全表](32b-loop-全表.md)）。

## ★ 不可變字面值是免費的

這條是量出來才發現的，而且很有用：

```janet
(for i 0 300000 [1 2 3])     #  1.2 ms   ← 常值 tuple
(for i 0 300000 @[1 2 3])    # 10.5 ms   ← 常值 array
(for i 0 300000 [i i i])     #  8.9 ms   ← 內容要算的 tuple
(for i 0 300000 @[i i i])    #  8.3 ms   ← 內容要算的 array
```

看起來像「tuple 比 array 快八倍」——**不是**。用 `disasm`（見
[16 marshal 與自省](16-marshal-與自省.md)）反組譯就看得出真正的原因：

```janet
(disasm (fn [] [1 2 3]))
# :constants @[(1 2 3)]        ← 整個 tuple 就是一個常數
# :bytecode  @[(ldc 1 0) …]    ← ldc = load constant，直接載入

(disasm (fn [i] [i i i]))
# :constants @[]
# :bytecode  @[(push3 0 0 0) (mktup 2) …]   ← mktup = 執行期真的建一個
```

同樣的差別在字典也成立：

| 寫法 | 編譯結果 |
|------|---------|
| `[1 2 3]`、`{:a 1}` | **`ldc`**——編譯期就固定成一個常數，每次都是同一個 |
| `@[1 2 3]`、`@{:a 1}` | **`mkarr`／`mktab`**——每次真的建一個新的 |

**所以：內容固定的對照表、預設設定，用 `{}`／`[]` 寫是真的零成本**，
用 `@{}`／`@[]` 寫則是每次進到那行都重建一次。這替 [35](35-拷貝與凍結.md)
「能不可變就不可變」補上了效能理由——不只是安全，是真的比較便宜。

⚠ 但**內容要算的時候兩者一樣貴**（8～11 ms，兩邊互有勝負，差異在雜訊範圍內），別為此改用 tuple。

## 怎麼自己量

```janet
(defn 計時 [名 f]
  (def t0 (os/clock :monotonic))     # ⚠ 一定要 :monotonic
  (f)
  (printf "%s %.1f ms" 名 (* 1000 (- (os/clock :monotonic) t0))))
```

⚠ **一定用 `:monotonic`**，不要用牆上時鐘——理由（NTP 校時會讓你量到負數）見
[24 時間與日期](24-時間與日期.md)。`spork/test` 也有現成的 `timeit`／`timeit-loop`
（見 [23b](23b-用-spork-test-寫測試.md)）。

量的時候三件事：**跑夠多次**（單次太短，時鐘解析度會蓋過訊號）、
**先跑一輪暖身**、**比倍數不比絕對值**。
