# 34 · 讀錯誤訊息與除錯

[20 錯誤處理](20-錯誤處理與資源管理.md) 教的是**怎麼拋、怎麼接**。這篇教**怎麼讀**——
Janet 的錯誤訊息有幾個地方會誤導你，知道了就能省下大量瞎猜的時間。

## 先分類：三種錯誤，格式完全不同

看第一行就分得出來，而且**能不能用 `try` 接是不一樣的**：

| 類別 | 長怎樣 | 什麼時候發生 | `try` 接得到嗎 |
|------|--------|-------------|---------------|
| **parse error** | `檔:行:列: parse error: …` | 括號沒收、字串沒關——**檔案根本沒讀完** | ✘ |
| **compile error** | `檔:行:列: compile error: …` | symbol 不存在、參數個數不對——**讀完了但編不成** | ✘ |
| **runtime error** | `error: …` ＋ 下面一串 `in …` | 真的跑起來才炸 | ✓ |

```
e.janet:2:0: parse error: unexpected end of source, ( opened at line 1, column 1
e.janet:1:1: compile error: unknown symbol 未定義的東西
error: 壞了
  in 裡 [e.janet] on line 1, column 15
```

⚠ **前兩類 `try` 包不住**，因為它們發生在「開始跑」之前。
[33 講的 arity 檢查](33-函式參數與閉包.md)就屬於 compile error——這是新手最常誤會的一點：
`(try (f) ([e] e))` 完全攔不到參數個數寫錯。

**只有第三類有堆疊**。有 `in …` 就是執行期，沒有就是前兩類。

## 堆疊怎麼讀：由內往外

```janet
(defn 第三層 [x] (error "最裡面炸了"))
(defn 第二層 [x] (+ 1 (第三層 x)))
(defn 第一層 [x] (第二層 x))
(第一層 42)
```

```
error: 最裡面炸了
  in 第三層 [t1.janet] on line 1, column 21
  in 第二層 [t1.janet] (tail call) on line 2, column 26
  in thunk [t1.janet] (tail call) on line 4, column 1
```

- **第一行是最裡面**，往下是呼叫它的人——跟 Python 相反、跟 C++ 的 gdb `bt` 相同。
- **`in thunk`** = 檔案的頂層程式碼（不在任何函式裡）。看到它就是「追到檔案最外層了」。
- 行號指的是**那一格所在的那一行**，不是錯誤本身那一行。

### ⚠ 尾呼叫會把中間那層**吃掉**

上面那個例子裡，**`第一層` 根本沒出現在堆疊裡**。因為 `(defn 第一層 [x] (第二層 x))`
的呼叫在**尾位置**，Janet 直接把 `第一層` 的 frame 換成 `第二層` 的，沒有留下痕跡。

改成三層全部尾呼叫，堆疊會縮到只剩兩行：

```
error: 尾呼叫版炸了
  in 第三層 [t2.janet] (tail call) on line 2, column 21
  in thunk [t2.janet] (tail call) on line 5, column 1
```

`第一層`、`第二層` **兩層全部消失**。所以：

> **「我的函式沒出現在堆疊裡」不代表它沒被呼叫**，很可能只是它做的是尾呼叫。

行尾那個 `(tail call)` 標記就是線索：**它表示這一格自己做了尾呼叫**，
所以它跟下一格之間可能還藏著看不到的層。要看到完整堆疊，就在中間隨便加一個
非尾位置的動作（例如把結果包進 `(do … )` 之外的運算），或直接在那裡插 `print`。

這是**遞迴深度不會爆的代價**：尾呼叫最佳化讓 Janet 能無限遞迴，換來的是堆疊資訊變少。

## 常見錯誤訊息翻譯

| 你看到的 | 實際意思 |
|---------|---------|
| `unknown symbol X` | 名字打錯，或 `import` 忘了寫／寫在函式裡（見 [05e](05e-import-與模組路徑.md)）|
| `<function f> expects at least N arguments, got M` | 參數個數不對，**compile error**，`try` 攔不到 |
| `nil called with N arguments, possibly expected 1` | 你呼叫的東西是 `nil`——通常是名字打錯或模組沒載到 |
| `could not find method :+ for 1 or :r+ for "a"` | **型別錯**。`(+ 1 "a")` 這種。Janet 的運算子會去找方法，所以訊息不像型別錯 |
| `expected integer key for tuple in range [0, 2), got 9` | 索引超出範圍 |
| `could not find module ./x:` ＋ 幾行候選路徑 | 路徑錯。**那幾行就是它逐一找過的地方**（`.jimage`／`.janet`／`/init.janet`／`.so`），照著看少了哪個 |
| `unknown method :a invoked on 5` | 拿 keyword 當方法用在不支援的值上（`(:a 5)`）|

### ⚠ 最誤導的一句：`expected string, symbol, keyword, array, tuple, table, struct or buffer, got 1`

```janet
(def f nil)
(f 1)   # => error: expected string, symbol, keyword, ... got 1
```

訊息在講**參數 `1` 的型別**，完全沒提「你呼叫了 nil」。為什麼？

因為在 Janet 裡**資料結構本身就可以呼叫，效果是索引自己**：

```janet
("abc" 1)     # => 98    等同 (get "abc" 1)
({:a 9} :a)   # => 9     等同 (get {:a 9} :a)
```

所以 `(f 1)` 在 `f` 是 `nil` 時被當成 `(get 1 nil)`——**它抱怨的是 `1` 不能被索引**。
給零個或兩個以上參數時就沒有這個歧義，訊息會變成好懂的 `nil called with N arguments`。

> 記法：**看到訊息在講一個你沒預期的型別，先確認你呼叫的東西是不是 `nil`。**

## 在程式裡印堆疊：`debug/stacktrace`

`try` 的 catch 可以拿第二個參數 `f`（出錯當下的 fiber），整個呼叫堆疊都還在裡面：

```janet
(try (外 1)
  ([e f] (debug/stacktrace f e "")))    # ← 第三個參數不能省
```

⚠ **第三個參數 `prefix` 不給就不印錯誤訊息那行**，只印 `in …` 那幾行。
傳 `""` 就得到跟程式自己炸掉時**一模一樣**的格式：

```
error: 壞了
  in 裡 [e.janet] on line 1, column 15
```

⚠ 它寫到 **stderr**，不是 stdout。所以在終端機上它跟你的 `print` 順序會錯亂
（兩條管線各自緩衝），要對照順序就 `2>&1` 導在一起看。

## `trace`：不改程式碼看某個函式被怎麼呼叫

```janet
(defn g [x] (* x 2))
(trace g)
(g 5)      # 先印 trace (g 5)，再回 10
(untrace g)
```

`trace` 把函式標記起來，之後每次呼叫都印一行 `trace (函式 參數…)`。
查「這個東西到底被呼叫幾次、參數是什麼」時比到處插 `print` 乾淨——
而且 `untrace` 就關掉，不用回頭刪。更多自省工具（`disasm`、`comptime`）見
[16 marshal 與自省](16-marshal-與自省.md)。
