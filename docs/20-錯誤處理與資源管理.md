# 20 · 錯誤處理與資源管理

C++ 有兩套工具：例外（`throw`/`try`/`catch`）跟 RAII（解構子）。
Janet 也有對應的兩套：`error`/`try` 跟 `defer`/`with`。差別在細節，這篇把差別講完。

## 拋錯與接錯

```janet
(error "boom")                      # 拋出

(try
  (error "boom")
  ([err] (print "抓到：" err)))     # => 抓到：boom
```

跟 C++ 最大的不同：**`error` 可以丟任何值，不必是「例外類別」**。丟 table 就是你的
結構化錯誤，比自己定義一整棵 exception class hierarchy 省事得多：

```janet
(try
  (error {:code 404 :msg "not found" :url "..."})
  ([e] (if (= 404 (e :code)) (print "找不到") (propagate e))))
```

`propagate` 相當於 C++ 的 `throw;`（重新拋出），把你不想處理的錯往上丟。

### catch 區塊可以拿到第二個參數：fiber

```janet
(try
  (error "z")
  ([e f] (debug/stacktrace f e)))    # f 是出錯當下的 fiber，可以印堆疊
```

Janet 的 `try` 底層就是「用一個攔 error 信號的 fiber 跑 body」，所以錯誤現場的整個
呼叫堆疊都還在那個 fiber 裡——這是它比 C++ 例外好用的地方，見 [09-fiber.md](09-fiber.md)。

### 不想用 try：protect

```janet
(protect (error "bad"))     # => (false "bad")
(protect (+ 1 2))           # => (true 3)
```

回傳 `(成功? 值)`，很像 Rust 的 `Result` 或 `std::expected`。適合「錯誤是預期內的一種結果」
的場合，不必為了流程控制去寫 try 區塊。

### errorf 與 assert

```janet
(errorf "檔案 %s 讀不到（code %d）" path 2)   # 等於 (error (string/format ...))

(assert (number? x) "x 必須是數字")           # 條件為假就拋錯
(assert (os/stat path))                        # 也能當「一定要有值」用，回傳該值
```

`assert` 在 Janet **不會被最佳化掉**（沒有 `NDEBUG` 這回事），它就是一般的執行期檢查。
在動態型別語言裡，`assert` 是補回型別檢查最省力的方式——函式開頭卡住前提條件，
壞資料就不會流到三層之外才爆炸。

## 資源管理：defer 與 with

沒有解構子，但有兩個巨集。

### defer：離開這個區塊時一定執行

```janet
(defn work []
  (defer (print "收尾")       # 第一個參數是「離開時要跑的」
    (do-something)             # 之後的才是 body
    (error "炸了")))
(try (work) ([e] (print "caught " e)))
# 印出：收尾  →  caught 炸了
```

**正常結束、提早 return、拋錯，三種情況都會執行**——這就是解構子給你的保證。
注意參數順序跟 Go 相反：Janet 是「收尾動作寫前面，body 寫後面」。

### with：開了就一定關

```janet
(with [f (file/open "x.txt" :rb)]
  (print (file/read f :all)))
# 離開時自動呼叫 (:close f)
```

`with` 預設呼叫該值的 `:close` 方法。物件沒有 `:close`、或要換一個收尾函式時，
第三個位置自己指定：

```janet
(with [conn (db-connect) db-disconnect]
  (query conn "..."))
```

心法：**`with` = 局部作用域版的 RAII**。C++ 是「物件活多久，資源活多久」；
Janet 是「這個區塊多長，資源活多長」。因為有 GC，「物件被回收時」的時機不可預期，
所以 Janet 乾脆不把資源綁在生命週期上，改成綁在明確的區塊上。

⚠ 推論：**別把 file handle 存進一個長命的 table 然後指望它會被關掉**。
handle 一定要有一個明確的擁有者（某個 `with` 區塊）決定它什麼時候關。

## 三者怎麼選

| 情況 | 用 |
|------|-----|
| 檔案 / socket / 子行程，開了要關 | `with` |
| 要還原某個狀態（改回 cwd、解鎖、印收尾） | `defer` |
| 錯誤是意外，希望往上炸 | `error` + 上層 `try` |
| 錯誤是預期內的分支 | `protect` 或回傳 `nil` |
| 檢查前提條件 | `assert` |

## 慣例：什麼時候回 nil，什麼時候拋錯

Janet 內建函式本身就分兩派，照抄它們的習慣就好：

- **查不到很正常** → 回 `nil`。`(get t :missing)`、`(string/find "z" "abc")`、
  `(os/stat "nope")`、`(scan-number "abc")` 都是這派。
- **這件事本來就該成功** → 拋錯。`(slurp "nope.txt")`、`(json/decode "{壞掉")` 是這派。

回 `nil` 的好處是能直接接條件式，不用開 try 區塊：

```janet
(if-let [size (os/stat path :size)]
  (printf "%d bytes" size)
  (print "檔案不在"))

(-?> config (get :server) (get :port))    # 中途 nil 就短路，不會炸
```

`-?>` 就是安全鏈式存取，相當於別的語言的 `?.`。

## 最後：錯誤訊息要能定位

動態型別最痛的一點是**錯誤在很遠的地方才爆**。實務上兩個習慣可以省掉大量 debug 時間：

1. 函式入口 `assert` 卡前提，訊息裡寫清楚拿到的是什麼：
   ```janet
   (assert (dictionary? cfg) (string/format "cfg 應該是 table，拿到 %q" cfg))
   ```
2. 往上拋之前**補上下文**，別讓一個 `"not found"` 從三層底下冒出來：
   ```janet
   (try (load-config path)
     ([e] (errorf "讀設定檔 %s 失敗：%q" path e)))
   ```
